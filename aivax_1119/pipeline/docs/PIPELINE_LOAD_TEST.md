# Pipeline worker 4개 성능 측정

측정 시작: 2026-10-17 18:58 KST.

실제 Pipeline 앱과 전용 Valkey를 사용해 필터 실행, INPUT/OUTPUT 병합, 최종 NDJSON 로그,
파일 보관 및 이벤트 발행을 함께 확인했다. 기존 운영 프로세스와 설정은 변경하지 않았다.

현재 runner의 자동 생성 DOCX는 Fasoo `DocProperties.setCTProperty()`로 태깅하고
재조회하여 검증한다(JDK 17 이상 필요). 태깅은 부하 측정 전에 수행한다.
이 문서의 기존 측정값과 파일 크기는 XML 속성 직접 생성 fixture를 사용한 기록이다.

## 측정 조건과 단위

- HTTP worker 4개, Python 3.13, uvloop/httptools. CSO가 활성화된 경우 worker당 JVM 1개.
- 프로세스 CPU affinity는 48개 논리 CPU다. 운영 systemd의 4 CPU 제한은 적용하지 않았다.
- 프롬프트 4,096바이트, 정규식 정책 100개, 파일 본문 정책 20개를 전용 Valkey에 발행했다.
- 정책은 사전 컴파일 가능한 단순 정규식이다. 차단 사례는 마지막 정책의 토큰에 일치한다.
- DOCX는 O 등급의 약 37KB 파일이다. 동일 템플릿의 요청별 hard link를 만들어 실제 검사·이동한다.
  원본 템플릿은 유지하며, OS 파일 캐시가 데워진 조건이다. DOCX 본문은 72,000바이트다.
- 각 경로에서 100세션을 준비 실행한 후 동시 세션 4·16·64개를 단계별로 측정했다.
- 각 단계는 10초 동안 새 세션을 생성하고, 이미 전송한 요청이 끝날 때까지 기다린다.
- closed-loop aiohttp, `debug=false`. 요청마다 TCP 연결을 닫아 worker에 트래픽을 분산한다.
- 표의 **세션/초**는 완료한 대화 단위다. 통과 및 Mirror는 INPUT + OUTPUT 두 번의 HTTP 호출,
  차단은 INPUT 한 번이다. 전체 왕복 p95는 이 호출들을 완료하는 지연이며 LLM 생성 시간은 없다.
- 별도 포트·런타임·Fluent Bit spool 디렉터리·Valkey를 사용한다. 실제 Fluent Bit 전달과
  OpenSearch 적재, Management 소비, 외부 SLM/SecuXper, OCR은 포함하지 않는다.
- 테스트 factory는 원래 앱을 그대로 생성한다. worker 식별용 HTTP 헤더만 추가하고,
  첨부파일 서비스의 공유 경로 allowlist를 격리된 테스트 보관 디렉터리로 주입한다.
  파일 검사·경로 검증·이벤트 생성은 실제 구현을 사용한다.

## 경로

| 이름 | 실행 내용 |
| --- | --- |
| 로그 병합 | `input_filter` → Valkey INPUT 저장 → OUTPUT 병합 → 최종 파일 로그·사용자 이벤트 |
| 정규식 통과 | 위 경로 + 프롬프트 정규식 100개 검사 |
| 정규식 차단 | 마지막 정규식 정책에 일치 → 최종 차단 로그·동의 상태·정책/사용자 이벤트, OUTPUT 없음 |
| Inline DOCX + CSO | CSO → 프롬프트 정규식 → DOCX 본문 추출·파일 정책 검사·hash·보관·첨부 이벤트 → OUTPUT 병합 |
| Mirror DOCX | 즉시 접수 + 일반 필터·DOCX 검사/보관을 백그라운드 실행 → 실제 OUTPUT과 병합 |

Mirror는 CSO 설정을 활성화한 상태에서도 가드를 실행하지 않는지 확인했다.
최종 로그에 `cso`가 없는지 검증했다. 설정에 따라 JVM은 기동하지만 등급 조회는 실행하지 않는다.

## 로그와 부수 효과 검증

정식 측정 114,064세션, HTTP 227,169회다. 준비 실행 500세션은 이 집계에서 제외한다.
HTTP/판정 오류 0건, 최종 로그 누락 0건,
중복 0건, 내용 검증 실패 0건이다.
INPUT과 OUTPUT이 다른 worker에서 처리된 쌍 78,698건에서도 로그가 정상 병합됐다.
각 단계 종료 시 Valkey의 INPUT/OUTPUT 병합 대기 key가 없는지 확인했다.

- 모든 `message_id`가 최종 NDJSON에 정확히 한 번 있는지 확인했다.
- 프롬프트와 실제 OUTPUT 텍스트의 일치, 차단 시 최종 차단 로그를 검사했다.
- 필터 실행 시각과 오류 필드를 검사해 미실행·실패를 정상 성능으로 집계하지 않았다.
- 파일 경로는 본문 chunk, SHA-256 hash와 실제 보관 파일의 존재를 확인했다.
- CSO 통과 로그는 O 등급을, Mirror 로그는 CSO 필드가 없음을 확인했다.
- 사용자·정책·첨부파일 이벤트의 전용 Valkey stream 길이를 기대 건수와 비교했다.
- 앱 ERROR 로그와 JVM 재시작도 확인했다. 원본 Java/class/JAR는 수정하지 않았다.

## Mirror 응답과 분석 완료 구분

Mirror의 INPUT p95는 접수 응답 시간이다. 분석 완료 지연으로 해석하면 안 된다.
응답 측정 후 모든 최종 로그가 나타날 때까지 기다리고 내용을 검증했다.
아래 처리량은 요청 완료 및 로그 확인에 걸린 전체 시간으로 나눈 보수적인 수치다.
추가 시간에는 로그 파일을 읽고 검증하는 테스트 자체의 비용도 포함된다.

## 정규식 차단 경로의 저장 병목

차단 경로는 동시 세션을 4 → 16 → 64로 높여도 약 28 → 29 → 31세션/초에 머물렀다.
INPUT p95는 226 → 702 → 2,289ms로 증가했다. 이 경로에서는 CSO와 파일 검사를 실행하지 않는다.

정식 측정 및 준비 실행의 필터 실행 기록 1,059건에서 정규식 검사 지연은
p50 0.486ms, p95 14.37ms였다. 별도 3초 진단 실행에서
`strace -f -T -yy -e trace=fsync,flock`로 실제 시스템 호출을 추적했다.
정식 성능 표는 strace 없이 측정한 결과다.

| 별도 진단 대상 | 표본 수 | p50(ms) | p95(ms) | 최대(ms) |
| --- | ---: | ---: | ---: | ---: |
| 동의 상태 파일 fsync | 104 | 29.27 | 62.06 | 226.38 |
| 공용 동의 상태 잠금 대기 | 104 | 538.69 | 662.96 | 680.98 |

[`FluentBitAnalysisLogDeliveryAdapter`](../src/adapters/analysis_log_delivery/fluent_bit_analysis_log_delivery_adapter.py)는
차단 로그를 기록할 때 `.consent-state/.lock`을 배타적으로 잡고, 메시지별 동의 상태를
`flush`·`fsync`한 뒤 잠금을 해제한다. 별도 추적에서도 fsync 동안 다른 worker/thread의
공용 잠금 대기가 이어졌다. 이 호스트의 저장 지연과 worker 간 직렬화가 차단 처리량을 제한한다.

상태의 내구성과 재시작·동의 재전송 계약을 유지하면서 잠금 범위와 동기 저장 전략을
검토하는 것이 후속 개선 지점이다. 이번 작업에서는 제품 동작을 변경하지 않았다.
추적 원본은 `.runtime/pipeline-block-io.strace`, 집계는
`.runtime/pipeline-block-io-summary.json`에 있다.

## 자원 사용과 해석 범위

| 경로 | Python worker RSS 합계 최대(MiB) | JVM RSS 합계 최대(MiB) | 부하 발생기 최대 CPU(한 코어 기준) |
| --- | ---: | ---: | ---: |
| 로그 병합 | 711 | 0 | 89.1% |
| 정규식 통과 | 710 | 0 | 82.9% |
| 정규식 차단 | 671 | 0 | 7.8% |
| Inline DOCX + CSO | 784 | 1,094 | 61.7% |
| Mirror DOCX | 842 | 224 | 80.9% |

RSS는 약 200ms 간격으로 수집한 관측 최대값이다. JVM 힙 옵션은 기본값이다.
부하 발생기와 서버가 같은 호스트에 있고, 부하 발생기의 단일 코어가 포화에 가까운 단계도 있어
이 결과는 서버의 최대 수용량이나 운영 보장치가 아니다. 정책 복잡도·문서 종류/크기·디스크·
CPU 제한·장시간 부하가 바뀌면 다시 측정해야 한다. 이전 CSO 결과는 입력 API만 측정했고
debug 응답과 정책·파일 검사 범위도 다르므로 처리량을 직접 나누어 비교하지 않는다.

## 재현

서버에 설치된 `valkey-server`가 PATH에 있어야 한다. 부하 도구는 이 실행 파일로
별도 Valkey 프로세스를 띄우고 임시 데이터·포트를 사용한다.

Pipeline 루트에서 실행한다.

```bash
/home1/aivax/aivax-venv/bin/python scripts/load_pipeline.py \
  --workers 4 --seconds 10 --concurrency 4 16 64 --warmup 100
```

일부 경로만 측정할 때는 `--profiles regex_allow regex_block`처럼 지정한다.
기본 결과 경로는 `.runtime/pipeline-load/<run-id>/report.json`이다.
이번 원본 결과와 profile별 설정·정책 cache·spool·프로세스 로그·DOCX는
`.runtime/pipeline-load-workers4/`에 보관했다. 종료 시 테스트 worker·JVM·Valkey를 회수한다.
