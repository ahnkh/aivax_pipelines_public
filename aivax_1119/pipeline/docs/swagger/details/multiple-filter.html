multiple_filter

POST /v1/filter/multiple_filter

사용자 프롬프트와 첨부파일을 검사하고, 호출자가 적용할 최종 보안 판정을 반환한다.

HTTP 200은 보안 허용이나 검사 성공을 뜻하지 않는다. final_decision.action과 action_code를 함께 확인한다. failed/0도 반환될 수 있다.

처리 흐름과 연결 키

  1. Content-Type: application/json으로 요청한다. INPUT과 OUTPUT에는 같은 message_id를 보낸다.
  2. Inline에서는 CSO 선행 검사를 수행한 뒤 정규식 → 첨부파일 → SLM → SecuXper 순서로 검사한다. 요청 목록에 있고 전역 설정에서 활성화된 필터만 실행하며, 요청 배열의 순서와 중복은 실행 순서에 영향을 주지 않는다.
  3. 일반 판정 우선순위는 block > masking > failed > accept > 빈 문자열이다. block에서 후속 검사를 중단한다. 각 필터는 앞 필터의 마스킹 결과 대신 원래 요청을 검사한다.
  4. 응답의 message_id를 실제 AI 출력의 output_filter 요청에도 사용한다. 일반 INPUT의 빈 ID는 서버가 생성하지만, 연결을 위해 클라이언트가 직접 같은 값을 전달하는 것을 권장한다.

필터 선택

전역 활성화 여부는 /etc/aivax/mode.json 설정 명세의 filters.<종류>.enabled로 정한다. 요청 목록에 포함되고 enabled=true인 일반 필터만 검사 후보가 된다. 설정 키와 요청 이름의 대응표, 생략 기본값, 변경 적용 방법은 링크에서 확인한다.

input_filter는 입력 로그 저장 요청이며 검사 필터가 아니다. secret_filter는 정규식, file_block_filter는 첨부파일, slm_filter는 SLM, secuxper_filter는 SecuXper 검사다. 알 수 없는 이름은 검사 전에 HTTP 404로 거부한다.

생략하면 다섯 필터 이름을 모두 요청한다. 빈 배열 또는 null은 일반 검사 대상이 없다는 뜻이다. CSO는 필터 목록과 독립적이므로 filter_list=[]로 CSO를 끌 수 없다.

사용자 동의 재전송

true 또는 문자열 on/1/true/yes/enable/enabled는 동의를 활성화한다. 문자열은 앞뒤 공백과 대소문자를 무시한다. 동의 요청은 원본 message_id가 필요하며 빈 ID는 HTTP 422다. Inline에서는 CSO를 통과하면 일반 필터 없이 accept/0, CSO 차단이면 block/1을 반환한다.

Mirror와 디버그

Mirror는 빈 action/0으로 즉시 접수하고 백그라운드에서 검사한다. 즉시 응답은 검사 완료를 뜻하지 않는다. 동의 전용 분기를 적용하지 않으며, debug=true여도 디버그 필드를 생략한다.

Inline의 debug=true에서만 filter_result, log_evidence가 추가된다. 요청 제외·전역 비활성화 필터는 생략하며, block 뒤 미실행 필터는 빈 기본 결과로 포함될 수 있다. 생성된 입력 로그가 없으면 log_evidence={}이며 최종 저장 완료 증명이 아니다.

SSL 우회 설정

AIVAX_PIPELINE_SSL_PROXY_BYPASS_BITMASK의 1은 block 우회, 2는 masking 우회, 3은 둘 다 우회다. 우회 대상 결과를 만나면 판정 취합을 끝내므로 일반 우선순위만으로 결과를 예측하면 안 된다. block 우회여도 필터 실행은 block에서 중단한다.

요청 필드

모든 필드에 기본값이 있지만, prompt는 생략하면 빈 문자열 대신 예제 문장이 사용된다. 원문과 연결 ID는 직접 전달한다. 정의되지 않은 추가 키는 기본적으로 무시한다. userConsent 대신 user_consent를 사용한다.

성공 응답과 필드

INPUT은 최상위 final_decision을 반환하며 out_result 래퍼가 없다. 미탐지의 빈 action, 명시적 허용 accept, 검사 실패 failed를 구분한다.
